## The single most important theme

**Dependency freshness is the top risk.** `next@16.2.6` carries 4 HIGH + 3 MODERATE unpatched CVEs including a **middleware/proxy-bypass** — and Strelva's entire auth gate lives in `src/proxy.ts`, which *is* the Next middleware. Bump to `16.2.12` first. Several security-pin `pnpm.overrides` are also frozen at now-vulnerable versions (brace-expansion, fast-uri, postcss, dompurify).

The second theme: **`DEFAULT_TENANT='demo'` silent fallbacks** in `getTenantFromHeaders`, the analytics GET route, and a Postgres shadow-write with no tenant filter — each a latent cross-tenant path if the proxy ever drops the `x-tenant` header.

## Confirmed Critical + High (28)

### 1. [CRITICAL · security] Next.js 16.2.6 has four HIGH + three MODERATE unpatched CVEs; auth gate is in middleware
**Area:** X-deps-supplychain — **`package.json:49`**

next@16.2.6 is pinned exactly. pnpm audit reports seven open advisories, all fixed at >=16.2.11: GHSA-6gpp-xcg3-4w24 (Middleware/Proxy bypass in App Router — HIGH), GHSA-m99w-x7hq-7vfj (DoS in App Router — HIGH), GHSA-89xv-2m56-2m9x (SSRF in Server Actions — HIGH), GHSA-p9j2-gv94-2wf4 (SSRF in rewrites — HIGH), GHSA-68g3-v927-f742 and GHSA-4633-3j49-mh5q (Cache confusion — MODERATE), GHSA-4c39-4ccg-62r3 (Unbounded Edge payload — MODERATE), GHSA-q8wf-6r8g-63ch (Image optimization DoS — MODERATE), GHSA-955p-x3mx-jcvp (Internal Server Action disclosure — MODERATE). The middleware-bypass CVE is especially acute here because all authentication lives in src/proxy.ts, which IS the Next.js middleware (renamed in Next 16). A bypass allows unauthenticated access to gated routes. Stable patch release is 16.2.12 (latest on npm at time of audit).

**Fix:** Bump next from 16.2.6 to 16.2.12 in package.json. Also bump eslint-config-next to match (currently pinned to 16.2.6 in devDependencies). Run pnpm install and re-run pnpm audit to confirm the Next.js advisories clear. The AGENTS.md note about `vercel --prod --yes --scope strelva` for env-var deploys applies here too — do a full fresh deploy after the bump.

### 2. [HIGH · bug] SUPABASE_URL (private, service-role) missing from env examples and production checklist
**Area:** X-config-env-deploy — **`src/lib/db/client.ts:29 / .env.example`**

The service-role Supabase client in client.ts reads process.env.SUPABASE_URL (the non-public var). Both .env.example and .env.production.example document only NEXT_PUBLIC_SUPABASE_URL. The production checklist (scripts/production-checklist.ts:158,1016) also only validates NEXT_PUBLIC_SUPABASE_URL. A developer following the example files, or an environment missing SUPABASE_URL, will cause getSupabase() to return null silently — disabling all service-role Postgres operations (tenant writes, dual-write shadow, governed-work reconcile, etc.) without any startup error. The production Vercel env has both set (confirmed in .vercel/.env.production.local) but the setup documentation doesn't reflect this and check:prod won't catch it.

**Fix:** Add SUPABASE_URL to .env.example (as a comment alongside NEXT_PUBLIC_SUPABASE_URL explaining it is the same URL but server-only), add it to .env.production.example under the Supabase block, and add checkEnvVar('SUPABASE_URL', true) to scripts/production-checklist.ts.

### 3. [HIGH · security] SECRETS_ENC_KEY absent from env examples and production checklist — at-rest encryption silently disabled
**Area:** X-config-env-deploy — **`src/lib/crypto/secrets.ts:26 / .env.example`**

AGENTS.md states SECRETS_ENC_KEY is ACTIVE in prod and secrets are enc:v1:-enveloped at rest. If this key is absent, encryptSecret() is a no-op (new writes stay plaintext) and decryptSecret() throws an Error only when reading a pre-encrypted value — not on write. A deploy with the key accidentally unset silently stores new OAuth tokens/webhooks/revalidation secrets as plaintext in Postgres while also breaking reads of already-encrypted rows. Neither .env.example, .env.production.example, nor scripts/production-checklist.ts mention this variable at all.

**Fix:** Add SECRETS_ENC_KEY to .env.production.example with a generation instruction (openssl rand -hex 32) and mark it required. Add checkEnvVar('SECRETS_ENC_KEY', true) to the production-checklist. Add a startup assertion in secrets.ts that warns (not throws) when key is unset and the db already contains enc:v1: prefixed values.

### 5. [HIGH · security] Five security-pin overrides are frozen at still-vulnerable versions
**Area:** X-deps-supplychain — **`package.json:73-97`**

The overrides block was written to pin known-vulnerable transitive deps to fixed versions, but several of those fixed versions have themselves received new CVEs since the pin was written: (1) brace-expansion@<2 pinned to 1.1.13 — CVE GHSA-3jxr-9vmj-r5cp requires >=1.1.16, so 1.1.13 is still vulnerable (DoS via exponential expansion). (2) brace-expansion@>=4 <5.0.5 pinned to 5.0.5 — the lockfile resolved to 5.0.6 (range upper bound does not cap the resolved version), and two newer CVEs (GHSA-3jxr-9vmj-r5cp for >=3.0.0 <5.0.7 and GHSA-mh99-v99m-4gvg for <=5.0.7) require >=5.0.8. (3) fast-uri unconditionally pinned to 3.1.2 — CVE GHSA-4c8g-83qw-93j6 and GHSA-v2hh-gcrm-f6hx both require >=3.1.4, so 3.1.2 is still vulnerable to host-confusion attacks. (4) postcss unconditionally pinned to 8.5.10 — CVE GHSA-6g55-p6wh-862q (arbitrary file read, HIGH) requires >=8.5.12 and GHSA-r28c-9q8g-f849 (path traversal, HIGH) requires >=8.5.18. (5) dompurify unconditionally pinned to 3.4.11 — CVE GHSA-c2j3-45gr-mqc4 (CUSTOM_ELEMENT_HANDLING bypass) requires >=3.4.12. pnpm audit shows 24 total vulnerabilities (14 high); these stale pins account for the majority.

**Fix:** Update each stale override: brace-expansion@<2 -> 1.1.16 (or higher); brace-expansion@>=3 <5.0.8 -> 5.0.8; fast-uri -> 3.1.4 (or drop the override and let pnpm resolve); postcss -> 8.5.18; dompurify -> 3.4.12 (or 3.4.13+). After each change run pnpm install then pnpm audit to verify the advisory count drops. The brace-expansion v5 range should also be updated since the installed version (5.0.6) is not what the range pin targets.

### 6. [HIGH · bug] Calendly webhook: addEvent call is unguarded — any Redis/Postgres failure returns 500 and triggers Calendly retry storm
**Area:** X-error-handling-edgecases — **`src/app/api/webhooks/calendly/route.ts:124`**

Line 124: `await addEvent({...})` is called with no surrounding try/catch. `addEvent` performs both a Redis enqueue and a Postgres insert; any transient failure throws an unhandled promise rejection, which Next.js converts to a 500 response. Calendly treats 5xx as a transient failure and retries the webhook, creating a retry storm that duplicates booking events in the governed-work queue once the transient error clears. The Stripe billing webhook (src/app/api/billing/webhook/route.ts) is the gold-standard comparison: every state-mutating call is inside a catch that marks the event failed and returns 200 to prevent re-delivery.

**Fix:** Wrap the `addEvent` call in try/catch. On catch, log the error and return a 200 (or 202) response so Calendly does not retry. Consider adding Redis idempotency keyed on `eventUri` (already present on the payload at line 107) to deduplicate any events that do get duplicated before this fix is deployed.

### 7. [HIGH · perf] Calendly webhook: redis.keys() full-keyspace scan in synchronous webhook handler path
**Area:** X-error-handling-edgecases — **`src/app/api/webhooks/calendly/route.ts:64`**

Line 64: `const keys = await redis.keys('calendly-meta:*')` performs an O(N) scan of the entire Redis keyspace on every incoming Calendly webhook. Redis `KEYS` is a blocking command — it blocks all other Redis operations for the duration of the scan. As the keyspace grows (with rate-limit keys, event queue entries, cache entries) this command becomes increasingly slow and blocks all Redis clients. In a multi-tenant deployment with thousands of keys this can add hundreds of milliseconds to every webhook and interfere with rate limiting and event processing on other requests.

**Fix:** Replace the scan-and-linear-search pattern with a reverse index. When a Calendly connection is saved, write `redis.set('calendly-user-uri:<userUri>', tenantId)`. Then `findTenantByUserUri` becomes a single O(1) `redis.get('calendly-user-uri:<userUri>')`. Clean up the reverse index key on disconnection.

### 8. [HIGH · perf] `buildOpsReport` has a fully serial N+1 loop — 3 sequential awaits per tenant, no concurrency cap
**Area:** X-performance-caching — **`src/lib/ops.ts:113-157`**

`buildOpsReport` runs three separate `for...of` loops over all active tenants sequentially. Loop 1 (lines 113-123): one `redis.get` per tenant for SMS pending state. Loop 2 (lines 126-145): `await getQueueCount(tenantId)` which itself calls `getEvents(tenantId, { status: 'pending', limit: 1000 })` — a `zrange` + batched `mget` — then `await getEvents(tenant.id, { status: 'auto_approved', limit: 100 })`. Loop 3 (lines 156-174): `await getTenantConfig(tenant.id)` per tenant. This is a pure N+1: at N=20 tenants that is ~60 sequential Redis round trips, all within the `buildPortfolioSnapshot` call that the `portfolio-snapshot` cron fires every 4 hours. The cron has `maxDuration=300` but the sequential structure will blow past acceptable latency well before the timeout at 50+ tenants.

**Fix:** Collapse the three `for...of` loops into a single `mapPool(active, 8, async (tenant) => { ... })` that fetches the SMS state, queue count, auto-approved events, and tenant config for each tenant in parallel. The SMS loop already produces independent, non-overlapping state per tenant, so there is no ordering dependency to preserve. The domain-drift loop can also be parallelized since `getTenantConfig` hits the Redis-cached `loadTenants` and is effectively free, but it still generates unnecessary repeated calls that a prior `getAllTenants()` already returned.

### 9. [HIGH · bug] customer.subscription.deleted never exercised at the webhook route level

Also assert that `alert('billing_subscription_cancelled')` fires.

### 10. [HIGH · bug] Stripe idempotency duplicate/retry/503 branches completely untested
**Area:** X-test-coverage-gaps — **`src/__tests__/billing-webhook-mode-guard.test.ts`**

The `claimStripeEvent` function in `webhook/route.ts` has four Redis-backed branches that all tests bypass (Redis is always null in tests, so `claimStripeEvent` short-circuits to `"claimed"` on line 40). The three live branches never tested are: (a) `"duplicate"` → 200 `{duplicate:true}` — a replayed event must not re-run; (b) `"retry"` → 503 — a concurrent-processing event must tell Stripe to retry rather than silently drop it; (c) `claimStripeEvent` throws (Redis down in prod) → 503 + `alert("billing_webhook_idempotency_unavailable")`. If the duplicate branch regressed to `"claimed"` (e.g., a broken `redis.get` always returns null), the idempotency guarantee collapses and a retried Stripe payment could double-update tenant status.

**Fix:** Add a `useFakeRedis()` helper variant for the idempotency tests. Test: duplicate event (Redis key already present with `status:"processed"`) → 200 `{duplicate:true}`, no `updateTenant` call. Test: in-flight event (status `"processing"`, recent `startedAt`) → 503. Test: Redis throws in `claimStripeEvent` → 503 + `alert("billing_webhook_idempotency_unavailable")` fires.

### 11. [HIGH · security] At-rest secret encryption (AES-256-GCM) has zero test coverage
**Area:** X-test-coverage-gaps — **`src/lib/crypto/secrets.ts`**

`encryptSecret` / `decryptSecret` in `src/lib/crypto/secrets.ts` wrap the four sensitive secret columns at the `rowToTenant`/`tenantToRow` boundary and are described as ACTIVE in prod since 2026-07-15. There is not a single test for these functions anywhere in the suite. The dual-mode read (legacy plaintext passthrough), the idempotency guard (`enc:v1:` prefix check), the keyless-safe passthrough, and the GCM auth-tag verification are all untested. A regression — for example, a decryption that silently returns `undefined` on a tampered ciphertext instead of throwing — could expose or silently swallow provider tokens (Google OAuth, Slack webhooks, revalidation secrets) without any test catching it.

**Fix:** Add a new `src/__tests__/secret-encryption.test.ts`. Test: (1) round-trip encrypt→decrypt with `SECRETS_ENC_KEY` set; (2) keyless pass-through with no `SECRETS_ENC_KEY`; (3) legacy plaintext pass-through (no `enc:v1:` prefix) still decrypts correctly; (4) `decryptSecret` throws on a tampered ciphertext (flipped auth tag); (5) `encryptSecret` is idempotent (already-encrypted value not double-encrypted); (6) null/undefined/empty preserved across both functions.

### 12. [HIGH · tenant-isolation] Missing Cache-Control: private on collections list and single-entry v1 routes
**Area:** api-v1-sync-contract — **`src/app/api/v1/collections/[tenant]/[type]/route.ts:39, src/app/api/v1/collections/[tenant]/[type]/[slug]/route.ts:38`**

The content, page-config, and site-capabilities v1 routes all set `Cache-Control: private, max-age=0, must-revalidate` (defined as TENANT_PRIVATE_CACHE). The two collections routes — both the list (`/collections/[tenant]/[type]`) and the single-entry (`/collections/[tenant]/[type]/[slug]`) — return their `NextResponse.json()` without any Cache-Control header. If a CDN or edge cache is ever placed in front (a realistic future state given the architecture is explicitly designed for it — the comment in content/route.ts explicitly says 'No CDN sits in front today, but this closes the latent cross-tenant bleed before one ever does'), a cached response for tenant A could be served to tenant B. The responses include the tenant's published collection entries (blog posts, products, videos), which may include business-sensitive pre-release content.

**Fix:** Define the same `TENANT_PRIVATE_CACHE = 'private, max-age=0, must-revalidate'` constant in both collections routes and include it in every successful `NextResponse.json()` response, matching the pattern already used in content, page-config, and site-capabilities routes. This is a one-line fix per route.

### 13. [HIGH · security] SSRF: AI-visibility scorer fetches user-supplied URL without pre-validation
**Area:** audit-and-ai-visibility — **`src/lib/ai-visibility/score.ts:80-95,283-293`**

The `fetchText` function in score.ts is a plain `fetch()` with `redirect: 'follow'` and no DNS pre-check. It is called with the user-controlled `url` field from `POST /api/ai-visibility`. Contrast this with `runAudit` in checks.ts which calls `validateUrlSafety(url)` (DNS lookup, family:4, `isPrivateIP` block) before any fetch, and re-validates the post-redirect host. The AI-visibility scorer has no equivalent guard, so an attacker can point it at http://169.254.169.254/ (IMDS), http://localhost/, or an internal service. The `robots.txt` fetch (`${origin}/robots.txt`) is also unguarded. The route does validate URL parse structure (`new URL(normalized)`) but that only rejects malformed strings, not private-IP destinations.

**Fix:** Import and call `validateUrlSafety(url)` from `src/lib/audit/checks.ts` at the top of `scoreAiVisibility` before the `fetchText` calls, matching the pattern in `runAudit`. Also add a post-redirect DNS re-check to `fetchText` itself (same as `buildAuditContext` in checks.ts:395-401) since `redirect:'follow'` can deliver the response from an internal host after a public-to-private redirect.

### 14. [HIGH · bug] Missing SECRETS_ENC_KEY removes env causes full platform outage via unguarded throw in loadTenants
**Area:** crypto-secrets-cron-concurrency — **`src/lib/tenants.ts:205-208, src/lib/crypto/secrets.ts:62`**

decryptSecret throws `new Error('SECRETS_ENC_KEY is not set but an encrypted secret was read')` when it encounters an enc:v1:-prefixed value without a key (secrets.ts:62). rowToTenant calls decryptSecret four times per row (lines 82-86). The .map(rowToTenant) inside loadTenants (lines 205-208) is NOT inside a try/catch. Once SECRETS_ENC_KEY is set and the backfill has run, ALL rows have enc:v1: prefixes. If SECRETS_ENC_KEY is ever accidentally removed or rotated incorrectly in Vercel env, loadTenants will throw on the first row, the uncaught exception propagates out of loadTenants, and every API route that calls getAllTenants (i.e., every cron) will crash with a 500. The in-memory cache has a 60s TTL so the outage begins within 60 seconds of an env change.

**Fix:** Wrap the rowToTenant call inside loadTenants in a per-row try/catch. On decrypt failure, either (a) skip the row and alert (so one bad row doesn't kill all tenants), or (b) re-throw a single aggregated error with a clear message naming the missing key. At minimum, add SECRETS_ENC_KEY to the production readiness checklist (productionEnvValidators in src/lib/production-readiness-rules.ts and checkEnvVar in scripts/production-checklist.ts) so a key removal is caught before deploy.

### 15. [HIGH · bug] GBP writes silently fail after tenant rename: google-meta key not in rename registry
**Area:** reviews-and-gbp — **`src/lib/tenant-rename.ts:32`**

The `google-meta:{tenantId}` key stores the GBP accountId + locationId obtained during OAuth and has a 1-year TTL set in the OAuth callback (`src/app/api/oauth/google/callback/route.ts:180`). It is the sole source for all GBP writes: `publishReviewReply`, `updateBusinessHours`, `createGbpPost`, `uploadGbpPhoto`, and the `poll-google-reviews` cron all call `fetchGBPMeta(tenantId)` which reads exactly this key. The key is NOT listed in `authoritativePatterns` in `tenant-rename.ts`. After a tenant slug rename, the key stays under the old slug; the new slug has no entry. Every GBP write silently returns `success: false, evidence: 'error=missing_account_location_meta'` until the owner explicitly reconnects Google — a failure the system surfaces only as a Slack ping and a pending failed-event, with no indication to the owner that a rename caused it. The comment at line 27 of tenant-rename.ts says caches 'regenerate from Postgres', but `google-meta` is not backed by Postgres — it is set only in the OAuth callback and lives exclusively in Redis.

**Fix:** Add `google-meta:${t}` to `authoritativePatterns` in `src/lib/tenant-rename.ts`. The key is a plain JSON object so the blob rewriter's `rewriteBlobTenant` may or may not touch it (the blob doesn't carry a `tenant`/`tenantId` field), but the key itself needs to be SCAN-moved to the new slug. Also add `review-replies:recent:${t}`, `reb:review-nudge-sent:${t}`, `reb:order-review-request-sent:${t}:*`, and `reb:review-reply-declined:${t}:*` (the declined-reply veto is 180 days durable and meaningful) to the registry. Update the completeness unit test assertions to cover these patterns.

### 16. [HIGH · bug] Fractional star delta causes uncaught Redis error in adjustStars
**Area:** rewards-booking-paylinks — **`src/app/api/rewards/members/[email]/adjust/route.ts:35`**

The adjust route validates `delta` with `Number.isFinite(delta) && delta !== 0`, which accepts any non-zero finite number including floats like 0.5 or -1.7. These are passed directly to `adjustStars`, which calls `kv.hincrby(memberKey, 'starsAvailable', delta)`. Redis HINCRBY requires an integer; the Upstash client propagates the protocol error as an uncaught exception, producing a 500 with no audit record of the attempt. The balance is left unchanged (the HINCRBY never applied) but the error leaks Redis internals to the caller.

**Fix:** Add `Number.isInteger(delta)` to the validation at route line 35, e.g. `if (!Number.isFinite(delta) || !Number.isInteger(delta) || delta === 0)`. Also validate in `adjustStars` itself as a library-level guard: `if (!Number.isInteger(delta)) throw new Error('delta must be an integer')` before the first hincrby call.

### 17. [HIGH · tenant-isolation] upload_image tool uses unscoped uploadFile() instead of uploadTenantMedia()
**Area:** tenant-content-agent — **`src/app/api/agent/route.ts:568`**

The agent's upload_image tool imports uploadFile from @/lib/storage (src/lib/storage/upload-store.ts) and calls it with no tenant argument. uploadFile puts the file directly into Vercel Blob at a flat path (just the sanitized filename with addRandomSuffix). The proper tenant-scoped path is src/lib/media-store.ts:uploadTenantMedia(), which prefixes every upload with media/{tenant}/ and is what show_photos/listTenantMedia reads. As a result: (a) images uploaded via the agent chat cannot be found by show_photos because they are not under the media/{tenant}/ prefix; (b) there is no tenant prefix on the Blob object, so deprovision/rename workflows that sweep media/{tenant}/ will silently miss agent-uploaded images; (c) all agent uploads land in the same flat namespace, making it impossible to enumerate or delete them per tenant.

**Fix:** Replace the uploadFile call in the upload_image tool execute() with uploadTenantMedia(tenant, buffer, finalFilename, sniffed). Remove the intermediate File/Blob construction — uploadTenantMedia takes a Buffer directly. The sniffed MIME type (from sniffImageType) should be passed as contentType, removing the need to re-parse the data URL type. This also fixes the AVIF bug below as uploadTenantMedia accepts any MIME type that sniffImageType returns.

### 18. [MEDIUM · bug] Calendly webhook: new Date(undefined) produces 'Invalid Date' string in stored event body
**Area:** X-error-handling-edgecases — **`src/app/api/webhooks/calendly/route.ts:129`**

Line 122: `const startTime = scheduled_event?.start_time || payload.payload.event?.start_time` evaluates to `undefined` when both fields are absent (Calendly cancellation variants and some event types omit `start_time`). Line 129 then evaluates `new Date(startTime).toLocaleString()` — `new Date(undefined)` is `Invalid Date`, so the stored event body reads `"New booking: Alice scheduled for Invalid Date"`. This is not caught anywhere; the `addEvent` call accepts the malformed string silently. `startTime` being undefined also means `metadata.scheduledTime` is stored as `undefined`, losing the booking time entirely.

**Fix:** Guard `startTime` before use: `const startTimeStr = startTime ? new Date(startTime).toLocaleString() : 'time TBD'`. Also validate that `startTime` is a string before passing it to `new Date()`. Store `startTime ?? null` in metadata rather than `undefined`.

### 19. [MEDIUM · perf] Triple `pgMetricSummary` RPC per report — 3 identical DB calls where 1 would do
**Area:** X-performance-caching — **`src/lib/storage/analytics-store.ts:166,302 and src/lib/reports.ts:505-513`**

`generateWeeklyReport` calls `getClickCounts('page-view', tenantId)`, `getClickCounts('booking-click', tenantId)`, `getClickCounts('phone-click', tenantId)`, and `getClickCountsByPrefix('booking-click:', tenantId)` inside a single `Promise.all`. Each of the first three calls `pgMetricSummary(tenant)` independently (analytics-store.ts:166), and `getClickCountsByPrefix` calls it a fourth time (analytics-store.ts:302). `pgMetricSummary` executes an RPC (`site_metric_summary`) or, on fallback, a full `pgAllRows` scan returning every metric/day/count row for the tenant. At report generation time with `mapPool(tenants, 6, ...)`, this means every active tenant triggers 4 identical Postgres RPC calls in one invocation. The fix is to call `pgMetricSummary` once, cache the result in a local `Map`, and pass it to each consumer — all four answers are already in the single RPC response.

**Fix:** Hoist `pgMetricSummary` to a module-level per-call memoizer (or pass the result as a parameter) so one Postgres round trip feeds `getClickCounts` for all three metrics and `getClickCountsByPrefix`. ### 28. [LOW · bug] Split-brain between content and draft/version stores due to two independent source flags

## Verified false-positives (2) — checked and dismissed

- **claimEventAction has no tenant isolation check** (`src/lib/events.ts:90-136`) — claimEventAction has exactly one production call site: event-actions.ts:174, inside resolveEventAction. That wrapper checks event.tenantId !== tenantId at line 104 and returns early with wrong_tenant before ever reaching claimEventAction. The finding's own text acknowledges "the current call path is safe" — the concern is purely speculative future misuse of the exported symbol, which is a code-hygiene observation, not an exploitable vulnerability in the deployed system.
- **Google reviews cron: data.expires_in cast without null-check throws on toISOString()** (`src/app/api/cron/poll-google-reviews/route.ts:88-94`) — The RangeError throw on `new Date(NaN).toISOString()` is mechanically real (lines 88-94 of /Users/noahowsiany/strelva-platform/src/app/api/cron/poll-google-reviews/route.ts), but the finding's core claim -- that the connection is left in 'connected' state and silently stops syncing -- is wrong. When `refreshAccessToken` returns `null` (whether from the RangeError catch or any other failure path), `pollTenant` handles it explicitly at lines 143-157: it calls `saveConnection({ ...connection, status: "needs_reauth" })` and fires a high-severity `alert("google_reviews_token_refresh_failed", ...)`. The connection is transitioned away from 'connected', the alert is not silent, and the dashboard will show "reconnect" rather than appearing to function normally. The described consequence (silent failure, stale 'connected' state) does not match the actual code path.
