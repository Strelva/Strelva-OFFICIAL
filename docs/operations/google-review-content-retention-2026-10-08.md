# Google API review content retention — prepared 2026-10-08

The actual Google polling path stored API comments in reviews.text and event.body, API author/rating/date in events and draft metadata, and exposed full reviews through schema-3 exports. Existing review rows and unified/governed event mirrors had no API-content expiry. Google's official GBP policy limits temporary secure API content storage to at most 30 calendar days and adds restrictions on manipulation/aggregation and use outside the project: https://developers.google.com/my-business/content/policies (checked 2026-10-08). This repair addresses the inspected review cache paths; it does not qualify all of those policy conditions.

Reserved additive migration 20261021100900 adds an explicit original fetchedAt/expiresAt provenance lease to Google API review rows. Valid leases last at most 29 days; future, malformed, extended or missing provenance fails closed. Replies, reply timestamps, manual reviews, review IDs, decisions, execution state and resolution history remain independent. Unknown legacy Google cache is scrubbed immediately on migration; it is not assigned a new collection date. No provider receipt1007/service/signed-owner-link changes are included.

New polling stamps the actual fetch once, uses a generic event body instead of duplicating the raw comment, and propagates the original lease into the reply proposal. API author/rating/context are projected out after expiry or without provenance. Review list/id reads, Redis event read/execution reads and updates, Postgres event list, schema-3 collection (including nested schema-2 snapshot), and native schema-3 review-row projection use the same boundary. Reply/event updates cannot renew the lease. The backlog refuses expired context and preserves the original lease for new drafts; due auto-posts refuse expired context.

The authenticated /api/cron/google-review-content-retention schedule is hourly and deliberately independent of listing/polling/drafting release flags. It physically scrubs review rows, unified event mirrors, governed proposal payload context, Redis event bodies and legacy embedded event-index members, and local dev review files. Existing event locks and original event TTL are retained. Missing DB/Redis, busy events or worker errors return503 and failed heartbeat, never a successful purge. The 29-day cache leaves one day of margin for the hourly job; scheduling/configuration/capacity must be operated and monitored to establish physical purge before day30. A missed or timed-out job remains an operational failure even though app reads redact expired content.

The inverse is explicitly forward-only: discarded API payload cannot be recovered, and reverting would restore indefinite caching. Historical SQL is unchanged. New functions/trigger helpers are not executable by anonymous/authenticated roles; only the purge command is service-role executable. Existing export authority stays with its original native functions.

## Pre-integration correction from independent review

The authenticated POST /api/reviews accepts platform label Google for customer-entered author/rating/text/date, and never accepts an external ID or caller-supplied provenance. Treating every source=google row as API cache was a preservation regression in the first prepared commit. The trusted route now stamps customer_import/authenticated_reviews_post; projections and SQL preserve that marker only without provider external identity. Client-supplied marker/external ID is ignored. An API-identified row cannot borrow the marker. New Google polling rejects a missing provider review ID before persistence.

Legacy reconciliation uses the inspected supported producers: accepted manual POST has no external ID and a complete required author/text/rating/date shape; Google API polling writes its reviewId. Only legacy Google rows with that complete manual-entry shape, no external ID/provenance and no matching API event (same original text/author and actual reviewId) receive the explicit legacy_reviews_post_no_external_id marker. This is producer-contract evidence and inference, not a declaration that arbitrary unknown Google text is customer authored. Identified API rows, incomplete rows and rows carrying matching API evidence remain fail closed. Preserve the observed criteria when assessing additional importers or historical sources; those are not qualified by this migration.

SQL event projection/trigger merges normalize metadata/payload to objects; SQL NULL, JSON null, scalar and array historical event shapes no longer fail subtraction or abort eager migration purge. Prepared populated predecessor upgrade fixtures are google-review-content-retention-upgrade-before.sql and -after.sql; apply1009 between them only in the coordinator's disposable clone. They cover supported manual import, identified API cache, ambiguous API mirror evidence, SQL/JSON null and scalar mirrors plus retained customer replies. They are unrun. The first retention commit must never be applied to data without this correction composed first.

Stored export parts are active Strelva-held copies, not externally downloaded copies. The archive correction therefore binds completion and both native token/verified-owner part readers to the original earliest provider-content expiry, caps the seven-day download lease, and checks the joined document again on both JavaScript download paths. Unknown or expired archived API content requires rebuilding; sealed chunks/checksums/manifest are never rewritten. Hourly purge invalidates the affected build, clears its token and physically deletes its parts while retaining request/manifest/receipt history and underlying customer records. Incomplete builds older than one hour are failed and their parts removed, limiting unsealed content even when a worker never completes. Legacy archive bodies are inspected before eager purge; unknown API provenance is not assigned a new build-date lease. Customer-import archives with trusted provenance retain their bytes.

The archive/native fixture includes day28 completion capped to its original near-term expiry, both real part-reader denials after expiry, physical part removal, retained receipt/request history and customer-import archive preservation. JavaScript tests exercise both actual multi-part download functions, prove day28 acceptance followed by original-expiry denial, and verify sealed bytes remain unchanged. Native execution remains pending. Storage/backup/operator capacity qualification still applies; a configured hourly cron is not proof it operates reliably.

Legacy file reads/purge use the same complete no-external-ID producer criteria and inspect the original Redis event evidence before that evidence is scrubbed. Unavailable history does not establish an import marker. Matching API evidence prevents promotion; the purge projects that row out before later reads could misclassify it from already-scrubbed event history. API-backed rows cannot change their source/external identity to launder the original cache into manual content, and raw anonymous/authenticated table writers cannot stamp trusted producer provenance.
