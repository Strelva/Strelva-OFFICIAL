# MCP streaming body admission — 2026-10-08

Actual handler `boundedBody` awaited full `request.text()` before checking JavaScript character length. Chunked bodies without Content-Length could allocate beyond the limit, and multibyte JSON could exceed30000 UTF-8 bytes while passing the character check. This happens before request validation/authorization but was not actually bounded during reading.

Prepared narrow source correction ports the reviewed streaming approach in local commit `0e6da815` into the current money lane: reject declared oversized bodies without pulling, read only bounded Uint8Array chunks, cancel when the next chunk crosses30000 bytes before retaining it, release the reader, then decode and parse the bounded buffer. Added fatal UTF-8 decoding so malformed bytes cannot be replaced silently into apparently valid JSON. Body rejection still uses existing400 Invalid JSON-RPC response and runs before authority, limiter or tools; no dependencies, authorization semantics, provider work, or production changes.

Actual handler regressions cover public/protected calls with cookie present, declared oversize zero pulls, no-Content-Length chunked oversize cancellation at crossing chunk, multibyte oversized JSON, exactly30000-byte success, UTF-8 codepoint split across chunks, malformed UTF-8, empty/malformed/nonobject JSON and zero Auth/tool/limiter calls on rejection. Focused platform MCP suite45 tests passed with maxWorkers2; scoped ESLint and diff check passed. No heavy/native/browser/server/provider window. Production transport/memory and full composed type/build checks remain coordinator-owned; a single upstream-produced oversized chunk already exists when delivered, but the parser neither appends nor concatenates it.
